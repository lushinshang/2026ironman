# Day 2 PRD — 贅詞與 AI 味檢查器

> 交付類型：**A 類**（GitHub Pages／下載 HTML，純前端執行，零外部函式庫依賴）

---

## 1. 背景與痛點

### 主情境：接續 Day1 字數統計的定稿前檢查

寫作者（尤其是用 AI 協作寫初稿的人）完成草稿、跑過 Day1 字數統計後，常常還沒處理掉「基本上」「其實」「就是說」這類贅詞，也沒發現「不僅如此」「值得一提的是」「賦能」「打造」這類 AI 生成文字常見的過渡語與抽象動詞高頻重複出現。人工逐句挑錯字很花時間，而且贅詞、AI 慣用語單獨看一次沒問題，只有整篇高頻出現才刺眼，肉眼很難抓出「整篇統計上」的重複。

### 延伸情境

- 審稿者想快速掃過一篇不確定是否為 AI 代寫的文章，看贅詞/AI 慣用語濃度。
- 行政人員潤飾公文、報告時，想清掉「針對~進行處理」「有關於」這類冗長套語（本次先標記提醒，不做語意改寫，見第 5 節）。

## 2. 目標使用者

- 主要：部落格／技術文章作者，尤其是用 AI 協作寫作、定稿前想清掉贅詞與 AI 腔的人
- 次要：行政人員潤飾公文報告；審稿者快速掃描文章的 AI 味濃度

## 3. 使用情境（User Story）

1. 身為用 AI 協作寫文章的作者，我把初稿貼進工具，系統依可編輯詞庫標出贅詞、AI 慣用語、抽象名詞的位置（標色但不自動刪除），我逐一勾選要刪的項目後點擊「執行刪除」才真正從文字中移除，避免自動誤刪掉語意需要的部分。
2. 身為想確認全文有沒有過度重複用詞的作者，我看到「不僅如此」「值得注意的是」這類詞在全文出現次數的統計，超過設定門檻（預設 3 次）才被標紅提醒，未達門檻的正常使用不受干擾。
3. 身為想自訂詞庫的使用者，我可以在詞庫區編輯／新增／刪除想抓的詞彙並標明分類（贅詞／AI 慣用語／抽象名詞），也可以匯出目前詞庫成 JSON 檔備份，之後匯入還原；偵測時「」『』內的引用內容不列入標記，避免誤判別人講的原話。

## 4. 功能需求（MVP，本次必須完成）

| # | 功能 | 說明 |
|---|---|---|
| F1 | 文字輸入 | 單一文字輸入區，支援直接貼上，也支援拖曳單一 .txt/.md 檔案自動帶入內容（沿用 Day9 的拖曳邏輯） |
| F2 | 主詞庫比對標記 | 內建可編輯主詞庫（每行「詞彙,分類」，分類為贅詞／AI慣用語／抽象名詞），對輸入文字做精確字串比對（非 regex，理由同 Day9 機敏字庫），命中處以底色標示，依分類不同顏色 |
| F3 | 詞彙人工確認刪除 | F2 標出的每一處皆可個別勾選（預設全部勾選），使用者按「執行刪除」才真正把已勾選的詞從文字中移除；未勾選的維持原樣，不自動改寫周邊句子 |
| F4 | 全文詞頻統計＋門檻標記 | 針對「高頻監測詞庫」（內建 AI 慣用過渡語清單，如「不僅如此」「值得一提的是」「總而言之」「換句話說」，可編輯）統計全文出現次數，達到使用者可調整的門檻（預設 3 次）才標紅提醒；此類標記僅提示、不提供一鍵刪除（因為要留幾次由使用者判斷） |
| F5 | 段落開頭同構偵測 | 依空行切段，取每段開頭前 N 個字（可設定，預設 5 字）比對重複次數，重複 ≥ 2 段以上才標記提醒該開頭；僅提示，不提供刪除 |
| F6 | 引號內容排除 | 「」『』""內的文字不列入 F2／F4／F5 的偵測範圍，避免引用他人原話被誤判 |
| F7 | 詞庫可編輯＋匯入匯出 | 主詞庫與高頻監測詞庫皆可在畫面上直接編輯（新增/刪除/改分類），並可各自匯出成 JSON 檔、匯入還原（做法比照 Day9 機敏字庫） |
| F8 | 統計摘要 | 顯示「贅詞命中 N 筆／AI慣用語命中 N 筆／抽象名詞命中 N 筆／高頻詞警示 N 組／段落開頭重複 N 組／已刪除 N 筆／可省字數」 |
| F9 | 複製與下載 | 一鍵複製處理後文字；一鍵下載處理後的 .txt 檔案 |

## 5. 非必要／可延伸功能（Nice to have，非 Day2 範圍）

- 冗長句型自動改寫（如「針對~進行分析」自動轉寫成「分析~」）：中文句型重組需要語法分析，純規則做不到，強做會產生錯誤句子，本次只標記整句提醒，不提供改寫
- 排比／強調句型的語法對稱性判斷：只能用固定連接詞組合詞庫比對（併入 F2 主詞庫），不追求偵測所有排比變體
- AI 味濃度百分比評分：屬語意判斷，純規則無法給出可信的量化分數
- 多檔案批次處理
- 詞庫的模糊比對或語意判斷（AI/NLP 判斷「這個詞在這裡算不算贅詞」）

> 上述功能明確排除於 Day2 MVP，避免範圍膨脹；若後續有需求再開新任務。

**已知限制**：主詞庫與高頻監測詞庫皆為精確字串比對，非語意判斷；同一個詞在不同語境下該不該算贅詞、算不算 AI 腔，工具無法判斷，一律列出讓使用者自己決定刪不刪。此限制會誠實寫進 README，不視為 bug。

## 6. 非功能需求

- **隱私**：所有偵測與統計皆在瀏覽器端完成，內容不上傳、不送出任何網路請求
- **零依賴**：字串比對、詞頻統計、段落切分皆為原生 JavaScript，不需要內嵌任何第三方函式庫
- **相容性**：Chrome／Safari／Edge 最新版正常運作；`file://` 協定下雙擊開啟需正常運作
- **效能**：單次輸入 1 萬字以內的文件，偵測與標示需在使用者可接受的時間內完成

## 7. UI/UX 需求

- 上方：文字輸入區（含拖曳提示）
- 詞庫設定區（可摺疊，預設收合）：
  - 主詞庫編輯區（贅詞／AI慣用語／抽象名詞，含分類標籤），匯入／匯出按鈕
  - 高頻監測詞庫編輯區＋門檻數字輸入（預設 3）＋段落開頭比對字數設定（預設 5 字）
- 「開始偵測」按鈕
- 偵測結果：原文以不同底色標示（贅詞／AI慣用語／抽象名詞可勾選；高頻詞警示／段落開頭重複僅標示不可勾選），需附色彩圖例
- 「執行刪除」按鈕：只針對可勾選類別、只刪除已勾選項目
- 底部顯示統計摘要
- 提供「複製處理後文字」「下載處理後 .txt」按鈕

## 8. 技術選型

- HTML + CSS + 原生 JavaScript，無外部函式庫
- 主詞庫格式：每行 `詞彙,分類`，分類限定 `贅詞`／`AI慣用語`／`抽象名詞` 三種，比對用 `indexOf`／字串比對，非 regex
- 高頻監測詞庫格式：每行一個詞，統計 `split` 後計數出現次數
- 段落開頭同構：以 `\n\n`（或連續空行）切段，取每段去除前導空白後的前 N 字，用 Map 計數重複
- 引號排除：正則抓 `「...」`、`『...』`、`"..."` 範圍，標記為排除區，比對迴圈時跳過該區間
- 內建初始詞庫（可由使用者調整/覆蓋）：
  - 贅詞：基本上、其實、就是說、說真的、老實說
  - AI 慣用語：不僅如此、值得一提的是、值得注意的是、總而言之、換句話說、不僅僅是、更是
  - 抽象名詞：賦能、賦予、打造、呈現、展現

## 9. 驗收標準（Acceptance Criteria）

1. 貼上含主詞庫三種分類（贅詞、AI慣用語、抽象名詞）各一筆的文字並執行偵測，三種類型皆需被正確標示且顏色不同。
2. 標示結果中取消勾選其中一筆，執行刪除後該筆內容需維持原樣、不被移除；其餘勾選項目需被正確從文字中刪除。
3. 高頻監測詞庫中的詞在全文出現次數低於門檻（如只出現 2 次，門檻設 3）時，不應被標紅；出現次數達到門檻時才標紅，且不提供勾選刪除選項。
4. 貼上兩段以上開頭前 5 字相同的文字（如皆以「首先，我們需要」開頭），執行偵測後需標記段落開頭重複；只有一段時不應標記。
5. 在「」或『』內放入含主詞庫詞彙的引用文字（例如 `他說：「基本上沒問題」`），執行偵測後引號內的「基本上」不應被標記。
6. 在詞庫編輯區新增一個自訂詞彙並標記分類後執行偵測，該詞需被正確標示；匯出詞庫 JSON 後清空詞庫再匯入，需完整還原原本的詞庫內容。
7. 拖曳 .txt 檔案到輸入區，需正確讀取檔案內容並帶入。
8. 點擊「下載處理後 .txt」需下載檔案，內容與畫面顯示的刪除後文字一致。
9. 開發者工具 Network 面板確認偵測與刪除過程無任何對外請求。
10. 直接以 `file://` 方式雙擊開啟 HTML 檔，貼上文字並執行偵測與刪除需正常運作。
11. 貼上一段完全不含任何詞庫詞彙、也沒有重複段落開頭的文字並執行偵測，統計摘要需顯示 0 筆，不誤判。

## 10. Out of Scope

- 不做冗長句型的自動改寫，僅標記提醒
- 不做排比／強調句型的語法對稱性判斷，僅用固定詞庫比對
- 不提供 AI 味濃度百分比評分
- 不支援批次多檔案處理
- 不做詞庫的語意判斷或模糊比對，僅支援使用者自訂詞彙的精確字串比對
- 高頻詞警示與段落開頭重複偵測不提供一鍵刪除，僅標示供使用者自行判斷
