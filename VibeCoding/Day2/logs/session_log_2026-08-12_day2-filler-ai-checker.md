## 換題決策過程

1. **需求強度檢視**：中英文排版工具的痛點已有 pangu.js 等成熟方案可解，純規則式準確度天花板也不高，需求強度判定偏弱。
2. **場景腦力激盪**：即使確認要做，也先完整跑過一輪使用場景（誰會用、輸入型態、例外情境、輸出行為），確認可行性邊界（純網頁零依賴只能靠規則式，做不到語意判斷）。
3. **重新推導整條流程**：使用者要求「用 Day1→Day5 的作業流重新推導」，逐一檢視五個步驟的痛點強度，發現不只 Day2 弱，Day5（QR Code／分享連結產生器）也偏弱。決定本次只換 Day2，Day5 先保留。
4. **定案新題目**：Day2 換成「贅詞與 AI 味檢查器」——定稿前檢查步驟，抓贅詞（基本上、其實）與 AI 慣用語（不僅如此、值得一提的是）。使用者追加要求「加上去 AI 味」，再一起做可行性篩選，排除「自動改寫句子」「排比結構語法對稱判斷」「AI 味百分比評分」三項純規則做不到的功能，收斂成「詞庫比對＋門檻標記，標記不改寫」的定位。

## 實作與驗證過程

逐條任務用 Playwright MCP 實際操作瀏覽器驗證，重點記錄：

- **F1 拖曳讀檔**：用真實 `DataTransfer`／`File` 物件模擬拖放，確認 `.txt` 內容正確帶入 textarea。
- **F2/F6 引號排除跨功能共用**：贅詞比對、高頻詞統計、段落開頭偵測三個功能都要套用引號排除，測試時故意設計「整段包在引號裡」的邊界情況（不只是引號夾在句中），驗證挖空引號範圍後再比對／切段的做法能正確避免誤判。
- **F4 高頻詞門檻**：測試資料刻意讓一個詞出現次數剛好卡在門檻下（2 次）、另一個剛好達門檻（3 次），驗證 `>=` 邊界寫得正確。
- **F7 匯入匯出**：用真實 File 物件模擬匯入流程（非只呼叫內部函式），確認詞庫匯出 JSON 後清空再匯入能完整還原（含使用者新增的自訂詞）。
- **AC10 file:// 驗證**：Playwright MCP 擋 `file://` 協定，改用本機已安裝的 Python playwright 套件直接開 `file://` 測試，確認雙擊開啟情境正常。

11 條驗收標準自測全數通過後，派一支獨立 fresh agent（不知道實作細節，只給 PRD 與原始碼）重新驗收，結果 11 條全過，agent 額外自行加測 3 個邊界情況（主詞庫詞彙互相重疊解析、空白輸入直接偵測、詞庫格式打錯逗號的容錯），也全數正常。
