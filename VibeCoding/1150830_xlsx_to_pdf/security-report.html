① .command：AppleScript 指令注入High

拖入的檔案路徑未經跳脫就直接用 Python f-string 拼進 AppleScript 原始碼。若路徑含 " 或換行字元，可跳出字串邊界注入任意 AppleScript 陳述式（進而執行任意 shell 指令）。這正是此工具的主要操作路徑（拖檔案進來），攻擊成本低。

修補方式

新增 asquote() 函式，跳脫路徑中的 \ 與 "，套用在組 AppleScript 字串前的所有路徑變數。

✅ 驗證：用含 " 的惡意檔名模擬注入 payload，實際跑 osascript round-trip，確認字串未被截斷、payload 未執行；py_compile 語法檢查通過。

② converter.html：innerHTML 未跳脫Medium

SheetJS 的 sheet_to_html() 對帶格式的富文字儲存格不會做 HTML escape，其輸出未經任何處理就直接寫入 innerHTML。惡意打造的 .xlsx 有機會夾帶 <script>、onerror 等標籤/屬性。

修補方式

新增 sanitizeSheetHtml()：用 DOMParser 做惰性解析（不會執行 script/事件），再用白名單（僅允許 table/tr/td/th/a/span，屬性僅允許 id/colspan/rowspan/data-*，<a> 只允許 http(s) 開頭的 href）過濾後才掛進真正的 DOM。

✅ 驗證：用瀏覽器實測 7 種 payload（<script>、onerror、javascript: href、onclick/onmouseover、svg onload/iframe、巢狀 table、form action=javascript:），清理後危險節點/屬性計數皆為 0；並用真實 16 個工作表的 xlsx 上傳比對清理前後文字內容，diff 為空，確認正常內容未被誤刪。

③ .bat：COM 未關閉巨集自動執行Low

透過 COM 開啟 Excel 檔案時未設定 AutomationSecurity，若拖入的檔案帶有 AutoOpen 巨集，會依使用者既有的巨集信任設定原樣執行。

修補方式

在兩個 PowerShell 分支的 Excel.Application COM 物件建立後，各加一行 $excel.AutomationSecurity = 3;（msoAutomationSecurityForceDisable）。

⚠️ 此項僅經靜態審查（位置正確、語法與周圍陳述式一致），因本機無 Windows/pwsh/Excel COM 環境，未經實際執行驗證。
後續功能追加的資安複查：新增「選擇檔案對話框」功能（讓使用者在雙擊執行、找不到檔案時跳出原生檔案選擇視窗）時，額外驗證了新流程沒有繞過上述①③的修補、沒有重新引入指令注入風險——選到的路徑一律沿用既有的 asquote() 跳脫鏈路與 PowerShell 變數傳遞方式，未新增任何字串拼接執行指令的路徑。

④ .bat：下載時被 Win11 SmartScreen / 瀏覽器擋下Low（非漏洞）

使用者回報從 index.html 下載 .bat 時被 Windows 11 資安防護擋住。這不是程式碼安全缺陷，而是下載信譽機制的使用體驗問題：瀏覽器對 .bat 副檔名本身列為常見危險副檔名並提高警覺，加上是全新網域、下載次數為 0，SmartScreen 應用程式信譽評分低容易被直接封鎖；腳本內容用 powershell -ExecutionPolicy Bypass -Command 呼叫 COM 自動化，這種樣式即使程式碼本身無害，也是 Defender/SmartScreen 常見的啟發式攔截特徵之一。

處理方式

改為提供 拖曳Excel至此轉PDF_Windows版.zip（.bat 內容完全未變動，僅打包），並在 使用手冊加入 SmartScreen 提示的處理步驟（點「其他資訊」→「仍要執行」，或右鍵內容解除封鎖）。

⚠️ 已用 diff 驗證解壓縮後 .bat 內容與原檔逐位元組一致。但本機無 Windows 環境，無法實測 SmartScreen 是否真的不再攔截——這是 Microsoft 雲端動態信譽評分，任何人都無法 100% 保證行為。此項僅採業界慣例最佳實務（打包 zip + 疑難排解文件），未經真實環境驗證。
