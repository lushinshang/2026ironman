## 🧠 3. AI 思考與自言自語紀錄 (Vibe Coding 日誌)

### 本日 Debug 與架構思考歷程：
1. **遇到的問題**：
   * 個資（身分證、手機、Email）有固定格式，可以用 regex 可靠偵測；但機敏資料（專案代號、金額、承辦人姓名）沒有固定格式，同一個詞在這份文件是機密、換個情境可能不是，regex 或語意判斷都不可靠。
   * 手機號碼（`09xx-xxx-xxx`）跟市話 regex（`0\d{1,2}-?\d{3,4}-?\d{4}`）在格式上會重疊——例如無分隔的 `0912345678` 同時符合兩種 pattern，若不處理會被重複標示兩次。
   * 遮蔽這種操作一旦做錯（誤刪不該刪的內容、或漏刪該遮蔽的個資）代價都很高，全自動無感執行風險太大。
2. **AI 的思考與解決路徑**：
   * 範圍決策：跟使用者討論後，把「個資」與「機敏資料」明確拆成兩層技術路徑——個資走 4 種 regex（身分證、手機、市話含分機、Email），機敏資料改用使用者自訂關鍵字清單＋精確字串比對（非 regex），不做語意判斷。這個決策在 PRD／提案階段就定案，避免實作中途才發現機敏資料規則做不出來。
   * 重疊去重：所有 regex 與關鍵字比對結果先各自收集成 `{start, end, type}` 陣列，合併後依起始位置排序、長度優先，再用一個簡單的「lastEnd」游標逐一過濾重疊區間——排在 `PII_PATTERNS` 陣列較前面的類型（身分證＞手機＞市話＞Email）優先保留，用 Node.js 手動跑過 `手機：0912345678` 這個案例驗證只會標記一次 `mobile`，不會跟 `landline` 重複。
   * 人工確認機制：偵測結果只標色附勾選框，不自動遮蔽；使用者可個別取消勾選，按下「執行遮蔽」才會真的替換文字，未勾選項目維持原樣——把 PRD 裡「不做全自動無感遮蔽」的決策落實成具體互動設計。
3. **最終解法與結論**：
   * 依 SDD 流程跑完 PRD（`Day4/PRD.md`）→ 提案（`sdd/day4-privacy-mask/proposal.md`＋`tasks.md`，8 條任務）→ 使用者確認「開始實作」後逐條完成。
   * 每條任務完成即時用 Playwright 對本機 `http.server` 做真實操作驗證，不接受「邏輯上應該對」：包含真實 `DragEvent('drop', {dataTransfer})` 拖曳測試（沿用 Day3 那次踩坑學到的教訓，不用 `input.files` + `change` 事件模擬繞過）、XSS payload（`<script>`、`onerror` 屬性）實測確認 `escapeHtml()` 正確轉義、Network 面板確認全程零對外請求。
   * 執行資安源碼檢測（見 `SECURITY_REVIEW.md`）：`innerHTML` 出現 2 處，皆確認資料來源已經過 `escapeHtml()` 轉義或為純數字；`eval`／`fetch`／`XMLHttpRequest`／外部資源載入皆為 0。本工具處理的內容本身就是個資，零對外連線是核心承諾，比 Day1～Day3 驗證得更嚴格。

```javascript
// 個資 regex 與機敏詞庫比對結果合併去重（Day4/index.html）
function mergeAndDedupe(matches){
  matches.sort(function(a, b){
    if (a.start !== b.start) return a.start - b.start;
    return (b.end - b.start) - (a.end - a.start);
  });
  var result = [];
  var lastEnd = -1;
  matches.forEach(function(match){
    if (match.start >= lastEnd){
      result.push(match);
      lastEnd = match.end;
    }
  });
  return result;
}
```

## 🔧 5. 擴充：個資規則式遮蔽 + 機敏字庫／代換字庫

上線後使用者回饋兩個體驗問題：個資遮蔽全部蓋成同一個 `[已遮蔽]`，看不出原本內容長什麼樣；機敏詞彙只能整段消失，沒辦法換成指定的替代寫法。經多輪釐清（詳見對話紀錄）定案兩個方向：個資改成依類型部分遮蔽、機敏詞庫拆成「機敏字庫」＋「代換字庫」兩個行號對應的輸入框，命中直接套用不用勾選。依 SDD 流程走完提案（`sdd/day4-rule-mask-substitution/proposal.md`＋`tasks.md`，8 條任務）→ 使用者確認「開始實作」→ 逐條完成、fresh agent 獨立驗收全數通過（過程中修正 3 處文件與實作不同步，見第 5 節）；已歸檔至 `sdd/archive/2026-08-10-day4-rule-mask-substitution/`。

**核心技術決策**：
* **姓名偵測**：內建約 60 個常見中文單姓字典，比對「姓氏＋緊接 1～2 個中文字」，屬啟發式判斷。用「王先生說王小明去開會」實測驗證：兩者都會被標成姓名候選（「王先生」誤判、「王小明」正確），符合 PRD 誠實記錄的已知限制，不追求 100% 準確。
* **個資規則式部分遮蔽**：身分證留頭尾中間用 ● 遮蔽（`A123456789`→`A●●●●●●789`）、手機/市話留末 3 碼、Email 的 @ 前只留第 1 碼、姓名留姓氏換 ○，取代原本統一的 `[已遮蔽]`，讓使用者還能辨識內容類型與長度。
* **機敏字庫／代換字庫行號配對**：兩個獨立 textarea 依行號索引一對一對應，機敏字庫命中時查代換字庫同一行——有值就直接代換、留空就退回 `[已遮蔽]`，且**不經過個資那套勾選確認流程**，偵測完成畫面上就已經是套用後的結果。

**過程中發現並修正一個真正的功能正確性 bug（非自驗，實測發現）**：初版 `detectAll` 把個資偵測結果放在合併陣列前段，導致「李永昌」這種同時符合姓氏字典（自動判成姓名 PII）又被使用者填進機敏字庫的詞彙，重疊去重時被自動偵測的姓名蓋掉，使用者在機敏字庫設定的代換／遮蔽完全沒有生效、也沒有任何錯誤提示——用 Playwright 實測「鳳凰專案由王小明負責...李永昌也參與」這段真實案例時發現統計數字對不上（機敏字庫命中數比預期少一筆），才追出根因。修法：把合併順序改成機敏字庫優先於自動偵測個資（`sensitiveMatches.concat(piiMatches)`），因為機敏字庫是使用者明確指定的清單，理應優先於自動猜測。修正後重新用同一案例驗證，「李永昌」正確退回 `[已遮蔽]`、不再被姓名標籤蓋掉。

**第二個發現並修正的 bug**：「執行遮蔽」按鈕統計的「已遮蔽」筆數把機敏字庫命中也算了進去，因為 `detectAll` 對所有比對結果（含機敏字庫）都預設 `selected:true`，而統計邏輯原本用「所有 selected 的項目」計數，沒有排除機敏字庫類別。修法：改成只計算 `category==='pii' && selected` 的項目。用同一測試案例驗證修正前後數字差異（修正前顯示 8 筆、修正後正確顯示 5 筆），確認是先前的計算方式有誤。

**驗收結果（11 條驗收條件全數通過，實作階段用 Playwright 逐條實測，非自驗推論）**：五種個資類型正確標示與部分遮蔽、取消勾選正確跳過、機敏字庫代換與退回遮蔽皆正確直接套用（不需勾選）、姓名反例符合已知限制描述、真實 DragEvent 拖曳成功、下載內容與畫面一致、Network 面板零對外請求、無誤判、代換字庫 XSS payload 正確逸出不觸發。`SECURITY_REVIEW.md` 已補上這輪的源碼檢測與重疊去重邏輯覆核記錄。
