## 背景

Day3 的程式碼與 6 輪追加修正（見 `README.md` 第 5～10 節）在前一個 session 已全數完成，但文章草稿完全還沒開始寫——不是寫完待潤飾，是 `Day3/` 目錄下連 `article_draft.md` 都不存在。這件事是使用者先問 Day1 文章「總編還在審查？」，AI 查證發現 Day1 的 Dashboard 措辭過於樂觀（README 進度勾選其實是未完成）後，使用者接著問到 Day3 文章的狀態才浮現。

## 提案階段（SDD 階段一）

使用者說「Day3 的文章 提案」，觸發 `sdd-flow` skill。AI 先讀了 `Day3/PRD.md`、`Day3/README.md` 全文（6 輪修正的完整歷程）、`CHECKLIST.md` 文章寫作規範，確認兩件真實情況後才動筆寫提案：

1. Day3 的開發歷程內容量遠超 Day1、Day2——6 輪真實文件迭代修正，多次用 `codex exec` 與 Opus 5 fresh agent 做對抗式驗收挖出真實 bug，是文章「Vibe 過程」的絕佳素材。
2. `Day3/index.html` 當時完全未 commit（`git status` 顯示 untracked），GitHub Pages 連結回應 404——這代表文章裡不能貿然放一個會 404 的線上體驗連結，是提案裡明確標註「需要使用者確認的前置依賴」。

建立 `sdd/day3-article/proposal.md`、`tasks.md`（8 條任務），貼重點給使用者並主動點出 GitHub Pages 連結的前置依賴問題，停下等確認；使用者說「開始實作」，但沒有直接回答連結要不要一併 push 上線——AI 判斷這不阻擋大部分寫作任務（T1～T6、T8），先動手，只在真正組裝連結的 T7 才處理，避免因為一個子問題卡住整個任務。

## 實作階段（SDD 階段二）：逐條任務

1. **T1／T2**：撰寫情境、解題思路、資源三節。情境延續 Day2 的合約改版比對情境，解題思路涵蓋 jsdiff 選型（先用 `npm pack diff@5` 實際下載檢查再定案，不是憑印象假設相容性）、斷句規則、修改配對邏輯設計。
2. **T3**：撰寫「Vibe 過程」——刻意不逐字照搬 README 第 5～10 節的 6 個小節標題，改成挑選最有讀者價值的幾個真實轉折（280 頁文件實測發現異常統計、Opus subagent 分類出 82～90% 雜訊佔比、`codex exec` 兩輪抓到門檻繞過漏洞、使用者提出的正規化方向被證實是共同根因）串成敘事。寫完立即掃描簡體字殘留，抓到一個「结果」的簡體字誤植，當場修正（跟先前 Day2 文章也發生過同類問題，這次有記得主動複查）。
3. **T4**：畫第二張 Mermaid 圖（三層 fallback 架構：位置索引配對→重新斷句配對→字元級錨點切分），跟 T1 那張（修改配對邏輯流程）一起用 `mermaid_check.py` 驗證語法，皆通過。
4. **T5**：起本機 HTTP server 載入 `Day3/index.html`，用 Playwright 灌入一份模擬合約條文（涵蓋新增/刪除/修改/未變動四種情境，且刻意設計成能讓連續 3 句觸發摺疊效果），實際點擊「開始比對」，確認畫面正確顯示「新增1／刪除1／修改1／未變動5」後截圖存檔（桌面版、手機版各一張）。
5. **T6**：撰寫心得與反思。
6. **T7**：組裝完整六段式格式（badge 列、目錄錨點、👉 引導行）。GitHub Pages 連結因為 `Day3/index.html` 仍未 push，明確標記為「待補」並附上原因說明，不放一個確定會 404 的網址；原始碼 repo 連結（Day3 目錄本身已有 PRD.md 等既有檔案）與 3 個 badge 逐一用 `curl -sI` 確認 200。
7. **T8**：呼叫 `editor-in-chief` skill 做總編審查。讀稿後判斷語言已經相當自然，只挑到一處「第一個是…第二個是…第三個是…」的大綱骨架外露段落——跟同一天稍早審查 Day1 文章時抓到的問題屬於同一類型，改成因果銜接的敘事語氣（「要不要自己寫 diff 演算法是第一個坎」「演算法定案後，斷句規則才是真正麻煩的地方」「斷句定案，接著要面對…」）。視覺實證（Mermaid、截圖、連結）在撰寫階段已經逐一驗證過，這輪沒有額外補。

每條任務完成即時在 `tasks.md` 打勾、簡短回報，沒有一次做完 8 條才回報。

## 獨立驗收（不自驗）

8 條任務全部打勾後，派一支全新、沒看過實作過程的 fresh agent，只給驗收條件與產出位置。Agent 自行決定驗證方式：`grep` 核對六段式結構與目錄錨點、抽取 Mermaid 區塊實際跑 `mermaid_check.py`、用 Read 工具實際打開截圖檢查畫面內容、逐一 `curl -sI` 驗證連結、Python 掃描簡體字、對照 README 確認文中統計數字有沒有根據。結論：**全部通過**，且額外確認文中數字（280 頁、6650/1005/2421/1088、513→246 等）都能在 `README.md` 找到對應依據，不是編造的。
