# Day 10：總表批次拆檔器——當驗收工具自己成了最大的假警報

![Day 10 概念圖：阿星與行政同仁將龐大的企業總表資料，透過瀏覽器瞬間拆分並打包進發光的 ZIP 壓縮盒](concept_art.jpg)

## 1. 情境：全台 50 間門市的盤點惡夢

「阿星，每逢月底盤點，我們行政組就全員加班到天亮……」

週五下午五點半，行政總監抱著筆電氣喘吁吁地走進來。他指著螢幕上一張整整四十萬列的「全台庫存大總表」，臉上寫滿絕望：

「總部系統每次倒出來就是這一大包。我們要寄給全台灣 50 間分店的店長核對，但每間店只能看自己家的庫存。以前的做法就是手動在 Excel 裡套篩選、選一間分店、複製貼到新工作表、另存成一個 CSV……連續重複做 50 次！只要手滑漏掉一間或複製錯範圍，整個週末的盤點就全毀了。」

「不能丟去外部轉檔網站一次切完嗎？」我問。

「那裡面有每間店的進貨成本跟營業額，怎麼可能敢放上公有雲？而且下班前店長們都在等檔案了！」

這種手動拆表的苦差事，大概每間公司都在重複上演。我們要做的東西其實需求很單純：一個能在瀏覽器本機端跑、不用裝軟體、依欄位自動把總表切成幾十份 CSV、再打包成一個 ZIP 的單檔工具。

## 2. 想法：中文檔名與 ZIP 容器的深水區

這個工具的核心邏輯看似不難：解析 CSV ➔ 依照選定的「分店名稱」分組 ➔ 各自組成 CSV 檔案。但當我們決定要提供「一鍵打包 ZIP」時，工程難度立刻跳入了另一個維度：**這是我們第一次在純前端瀏覽器裡，動態組裝二進位 ZIP 容器格式**。

### 挑選函式庫：零依賴與單檔打包的權衡

在單一 HTML 檔案的限制下，函式庫的體積與相容性是生死線：
- **JSZip**：老牌知名，但核心已近四年未維護，程式碼體積偏大。
- **client-zip**：體積非常輕量（約 6.5KB），但原生只提供 ESM 模組，難以無縫內嵌進我們的單檔 HTML。
- **自己造輪子（純手寫 store-only writer）**：雖然只要一百行代碼，但必須自己手動計算 CRC32 校驗碼與維護複雜的 ZIP 檔頭位元組結構，風險極高。

最終我們選用了僅 33KB 的 **fflate 0.8.3**：既能無痛內嵌打包，又自帶高效率的 DEFLATE 壓縮演算法，對純文字的 CSV 能提供極高的壓縮比。

### 檔名生成的安全防線

在作業系統中，拿使用者資料當作檔名是一場隨時會爆炸的冒險。分店名稱可能包含空格、全形標點，甚至特殊符號。我們必須為檔名建立一套嚴格的清洗管線：

```text
檔名安全清洗管線
--------------------
輸入原始群組字串
        |
        v
置換 Windows 保留字
< > : / \ | ? * -> _
        |
        v
清除 0x00-0x1F 控制字
        |
        v
修剪頭尾空格與結尾句點
(開頭句點保留，如.temp)
        |
        v
避開保留裝置名
(CON/PRN/AUX -> 加_group)
        |
        v
全底線字串 -> "未命名"
檔名衝突 -> 自動加 _2, _3
```

在這套規則中，我們查閱微軟官方檔案命名規範時發現了一個有趣的冷知識：很多人以為檔名不能有句點，但官方規範明確指出**「開頭句點完全合法（例如 `.temp`），只有結尾句點會被檔案系統強制吃掉而違規」**。

此外，若使用者欄位只有 `///`，經過置換會變成 `___`。如果放任它成為檔名，使用者在資料夾裡只會看到一串無意義的底線；我們在最後一道閘門將「純底線」強制歸類為「未命名」，並依序加上計數後綴。

## 3. 過程：當驗收工具自己成了最大的假警報

功能迅速開發完成，但在獨立驗收階段，我們卻撞上了一個讓所有人冷汗直流的靈異現象。

### 痛點一：驗收工具本身會騙人

當我們在 macOS 終端機測試產出的 ZIP 檔時，執行系統內建的 `unzip -l`，終端機竟然噴出了一整片亂碼；緊接著跑 `unzip -d` 解壓縮，系統直接無情中斷並報錯：

```bash
fatal error: Illegal byte sequence
```

所有人當下的第一反應都是：「天啊，fflate 產出的 ZIP 結構壞了？還是中文字串編碼有問題？」

如果此時病急亂投醫，開始去亂改 UTF-8 編碼或改動 ZIP 檔頭，我們就會陷入毀滅性的除錯死胡同。

冷靜翻查系統底層才發現：**有問題的根本不是我們產出的 ZIP，而是 macOS 內建的 `unzip` 工具！**
macOS 內建的 `unzip` 是 2009 年的 Info-ZIP 6.00 修改版，這個老舊版本在解壓縮時預設根本不支援現代 ZIP 的 UTF-8（EFS flag）。當檔名包含中文時，它會用老舊的編碼去解讀，硬生生觸發 `Illegal byte sequence` 崩潰。

```text
中文 ZIP 驗收陷阱
--------------------
產出正確 UTF-8 ZIP
        |
   +----+----+
   |         |
內建 unzip  系統 ditto
   |         |
不支援 EFS   macOS 原生解壓
噴出亂碼     中文完全正確
中斷崩潰     位元組 100% 吻合
(假性失敗)   (真實通過)
```

當我們改用 macOS 原生圖形介面（雙擊解壓走的 `ditto -x -k`）或是現代的 `bsdtar`、Python `zipfile` 模組來驗證時，50 個中文檔名全部清清楚楚、檔案內容一個 byte 也不差！

這件事讓我們學到一課：測試亮紅燈時，先別急著懷疑自己的東西壞了——有時候是量尺本身早就過期了。

### 痛點二：消失的警告樣式

在實測大檔案（例如上傳 6MB 以上的總表）時，我們發現了一個隱蔽的 UI 細節破綻：畫面確實顯示了「檔案較大，正在分組處理中...」的提示文字，但原本設計用來提醒使用者的黃色警告框與顯眼邊框，卻在解析瞬間被清空了。

追查代碼才發現，資料載入回呼函式在完成時，順手寫了一行 `uploadMsgEl.className = ''`，把大小閘門剛剛加上去的 `.warn` 樣式覆寫掉了。這提醒了我們：文字內容正確，不代表介面狀態傳達完整；視覺上的回饋感與狀態管理，必須與邏輯完全脫鉤。

## 5. 感想與明日伏筆

看著行政總監把那張四十萬列的全台大總表拖進網頁，短短三秒鐘，網頁就自動辨識出 50 間門市，點擊「全部打包下載」，一個乾淨俐落、只有 2MB 的 ZIP 壓縮檔瞬間出現在下載資料夾裡。

總監看著看著，臉上的表情從「這真的行嗎」慢慢變成「太好了可以準時下班」。

十天下來，從文字排版、AI 去油、資料去識別化，一路走到 CSV 的深水區——急診室診斷、跨期主鍵對照，再到今天的動態 ZIP 拆檔。沒有後端伺服器可以躲，逼著我們把瀏覽器記憶體控制、檔案安全規範這些細節，一項一項摸清楚。

正當大家準備收拾書包歡呼放假時，門口傳來了總經理的聲音：

「聽說你們剛做了一個能吃下幾十萬列庫存總表的工具？太好了！明天全台營運高層要開會，老闆想在離線筆電上，把這張大總表隨意拖拉維度、切換欄位做即時交叉分析。公司沒裝 BI 系統，能不能直接生一個出來？」

辦公室裡的歡呼聲瞬間凍結，大家齊刷刷地把目光投向了我。

看來這個週末，還是別想太早收工。
