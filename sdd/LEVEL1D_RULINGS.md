## 使用者明確裁決的 3 條

### 裁示 1：`pdf-review-stamper`（Day22）中文字型嵌入方案

**裁示：方案 A**（使用者 2026-08-24，「1.A」）——完整思源黑體 Noto Sans TC（OFL 授權），
接受檔案體積代價（預估數 MB 到十幾 MB），換取使用者可自訂任意中文浮水印文字。

**影響**：
- `sdd/pdf-infra/tasks.md` 任務 7 的字型嵌入驗證，實作時直接用 Noto Sans TC（或其
  Traditional Chinese 子集版本，若官方有分版本），不再用「任一份可取得的測試用字型」
  這種暫定用法。
- 下載來源、版本號、SHA-256 依 `shared/vendor/README.md` 慣例記錄。
- **檔案體積是已知代價，不是意外**——`Day22_pdf-review-stamper/index.html` 的下載
  體積會明顯大於本系列目前任何一題，這是裁示當下已知且接受的取捨，實作完成後
  誠實記錄實際數字，不需要因為體積大而回頭質疑裁示本身。
- `sdd/pdf-review-stamper/tasks.md` 涉及字型的任務，「暫用任一測試字型」的措辭
  改為明確使用 Noto Sans TC。

### 裁示 2：`pdf-organizer`（Day21）排序互動方式

**裁示：選項 A，真正的拖曳互動**（使用者 2026-08-24，「2.真拖曳」）——不採用
Day18 先例的按鈕方案，做 HTML5 native drag events 或 pointer-based 拖曳，含觸控裝置
相容性與拖曳時的視覺回饋（插入線／佔位格）。

**影響**：`sdd/pdf-organizer/tasks.md` 排序相關任務要包含真正的拖曳互動實作與
Playwright 拖曳操作驗收（`browser_drag`），不是按鈕點擊驗收。跨文件（縮圖來自不同
來源 PDF）與大量頁面（可能上百項）的拖曳效能與觸控相容性，屬於本題任務本身要處理
的範圍，不再是待裁示。

### 裁示 3：`pdf-organizer`（Day21）拆分輸出型態

**裁示：可以一份，也可以多份**（使用者 2026-08-24，「3.可以一份，可以多份」）——
採用提案「理解 B」並泛化：使用者可以定義**一組或多組**頁碼範圍／頁面選取結果，
每一組各自輸出一份 PDF；只定義一組時自然只產出一份（等同理解 A 的效果），定義
多組時一次產出多份（包成 ZIP 下載，複用 `io-zip.js`）。**不是理解 A 與理解 B 二選一，
是用理解 B 的介面涵蓋兩種情境**。

**影響**：`sdd/pdf-organizer/tasks.md` 需要「多組範圍→多份輸出」的介面（提案裡標記
為範圍擴增的部分），任務數量可能超過原本 8 條估計的 10 條上限，實作階段若真的
拆不進 10 條，依 `WORKFLOW.md` 第一階段規則提醒使用者拆案，不要硬塞。

## 授權代為決定的 17 條

以下依 `ops/JUDGMENT.md` 默認同意判準與指揮官「剩下幫我決定」的明確授權（2026-08-24）
逐條定案，全部採用各提案自己列出的「暫定」方案，除非另有註記理由偏離暫定值。

### `pdf-to-jpg`（Day19）— 3 條

1. **目標容量二分逼近**：採暫定，**不做**，只做品質滑桿（0–1）。理由沿用提案：
   跟 Day14 是不同產品定位，PDF 轉圖片場景對精確容量的要求不如批次壓縮明確。
2. **渲染倍率**：採暫定，縮圖 `scale: 0.3`、正式輸出 `scale: 2`（約 144 DPI）。
   實作時記錄實際輸出像素尺寸，若明顯不合理回頭調整，不视为違反本裁示。
3. **檔名規則**：採暫定，`{原檔名}_p{補零頁碼}.jpg`。

### `pdf-text-search`（Day20）— 4 條

4. **搜尋片段長度**：採暫定，關鍵字前後各 30 字元，同頁多命中各自列一則。
5. **模糊匹配範圍**：採暫定，只做英文大小寫不敏感，不做全半形／簡繁轉換。
6. **多關鍵字搜尋邏輯**：採暫定，MVP 只支援單一片語搜尋，不拆詞做 AND/OR。
7. **定位呈現方式**：採暫定，捲動到逐頁文字區塊並高亮，不額外渲染縮圖（避免非必要
   擴大對 `renderPageToCanvas()` 的依賴）。

### `pdf-review-stamper`（Day22）— 2 條（字型見裁示 1，不重複列）

8. **浮水印透明度／角度／位置預設值**：採暫定，透明度 50%、角度 45°、位置提供
   「左上／置中／對角線」三選項，對角線為預設。
9. **預覽方式**：採暫定，選項 (b) 按鈕觸發式預覽，不做即時渲染。理由：送審章通常
   一次設定套用全頁，不像 Day17 需要連續拖曳的即時回饋，實作複雜度也明顯較低。

### `pdf-password-manager`（Day23）— 3 條

10. **批次中部分檔案密碼錯誤時的行為**：採暫定，**不中止**，逐檔獨立顯示成功／
    失敗，繼續處理其餘檔案。
11. **加密演算法／金鑰長度是否曝露給使用者選**：**決定不曝露**。無論
    `sdd/pdf-infra/` 任務 8 實測結果支援單一還是多種演算法，UI 一律不做選項，
    保持介面單純——多數使用者不需要知道演算法細節，這屬於「PRD 沒要求就不做」
    的一貫原則。實測出的實際演算法版本號仍要記錄在 `pdf-infra` 的驗收報告與
    `PDF_CONTRACT.md`，供未來查閱，只是不做成使用者可見的選項。
12. **PDF 權限功能（列印／複製／編輯權限）**：採暫定，**不做**，避免 PRD 沒要求的
    範圍蔓延。`encryptPdf()` 的 `opts.permissions` 欄位在契約層級保留（`@cantoo/pdf-lib`
    原生支援），但本題不建立對應 UI。

### `pdf-secure-redactor`（Day24）— 3 條

13. **Rasterize 輸出畫質**：採暫定，`scale: 2`，**不做 UI 可選項**（不做「標準／高
    畫質」兩檔，保持介面單純，畫質與檔案大小的固定取捨已在裁示時知情接受）。
14. **框選區域形狀**：採暫定，沿用 Day16 既有裁示，矩形限定，不重新開形狀選型討論。
15. **移除單一框選區域的還原機制（未輸出前）**：採暫定，**要做**。框選是使用者
    互動中很自然會後悔的操作，不提供體驗會明顯變差，這條的技術成本也低。

### `pdf-delivery-cleaner`（Day25）— 2 條

16. **Action/JavaScript 類別偵測不到時的 UI 呈現**：採暫定，選項 (b)，顯示分類但
    誠實註明「本工具無法完整偵測此類物件，建議另用專業工具確認送出前無殘留 Action」。
    理由：資安/隱私工具隱瞞已知偵測盲區的風險高於誠實揭露，與專案一貫的誠實原則
    一致（`CHECKLIST.md` 第三節「誠實原則」）。
17. **附件掃描顯示深度**：採暫定，選項 (a)，只顯示附件檔名與大小，不做 (b) 額外
    metadata 也不做 (c) 下載／預覽附件內容——附件內容清理不是本題 MVP，只需要讓
    使用者知道「這份 PDF 裡藏了檔案」。

### `office-content-publisher`（Day26）— 3 條

18. **Markdown→HTML 轉換**：採暫定，**方案 B，手寫簡化版 parser**（不引入
    `marked` 或同類 library）。理由：與專案至今「手寫優先」的技術路線一致
    （`img-exif.js`／`img-perspective.js`／CSV parser 皆手寫），零依賴、零授權疑慮，
    且 PRD 場景（HackMD/GitHub/正式網頁）本身有各自的 Markdown 渲染器，本工具角色
    是快速轉出堪用 HTML，不追求完整 CommonMark 相容。實作時需在文案上明確告知
    使用者這是「簡化版」語法子集（標題／粗體／斜體／清單／連結／code fence），
    不是完整 Markdown 實作。
19. **「至少一種乾淨列印模板」的做法**：**決定選 (C)，正式升級為 `shared/print.css`**。
    理由：`IMG_CONTRACT.md` 訂下的「第三題才升級為共用」判準到 Day26 真的滿足了——
    Day13（`csv-one-page-report`）、Day18（`photo-evidence-sheet`）、Day26 三題都需要
    `@media print` 版型，不再是「未達門檻」的狀態。**這是一項連帶影響既有已上線
    產品的決定，需要額外任務**：
    - 從 Day13／Day18 現有的列印 CSS 抽出共通部分，新增 `shared/print.css`
    - Day13、Day18 改為引用 `shared/print.css`（比照 Level 1c `io-dropzone.js` 擴充
      的向後相容原則——抽出共用不改變既有輸出的視覺結果）
    - Day13、Day18 重新 bundle，`bundle_manifest.json` 的 sha256 會變動（因為多引用
      一個 SHARED 模組），這是預期中的變動，不是回歸
    - 完成後對 Day13、Day18 的列印輸出做視覺比對（重新 bundle 前後列印結果一致），
      確認抽取過程沒有意外改變既有行為
    - 這件事應該在 Day26 開工前，比照 `pdf-infra` 的模式作為一次小型前置工程完成，
      不要放進 Day26 自己的 `tasks.md`（Day26 只需要引用 `shared/print.css`，不負責
      抽取既有程式碼）
20. **CSV 欄位選擇／排序的 UI 型態**：**決定**簡單勾選框列表（選要輸出的欄）+
    下拉選單選排序欄位／方向（升冪/降冪），不做表格標頭直接點擊排序（後者互動
    效果更好但實作複雜度不成比例，PRD 沒有要求到這個程度）。排序邏輯**採用
    `csv-types.js` 的 `inferColumnTypes()` 做型別感知排序**（數字欄位當數字排序，
    非數字欄位當字串排序）——理由：Day08（`csv-doctor`）已建立這個能力且已驗證
    正確，直接複用比自己另寫一套字串排序更省工、行為也跟系列其他題目一致；
    `CSV_CONTRACT.md` 第 2 節「parser 不做任何貼心修正」約束的是解析階段，不涵蓋
    本題的呈現／排序邏輯，不衝突。
