## 為什麼做

文件交給外部人員或 AI 前，常要移除姓名、電話、Email 等資訊；工作完成後又可能要在本機把處理結果還原成原本的人名與聯絡方式。

v1 的對應作品（`VibeCoding/old/Day9/`）只做**單向遮蔽**：`A123456789` 蓋成 `A●●●●●●789`、機敏字庫命中換成代換詞或 `[已遮蔽]`，原文資訊當場丟棄，沒有任何 mapping 或 token 機制（已用 `grep -n` 全檔確認：`old/Day9/index.html` 無 `mapping`／`token`／`restore` 相關識別符）。因此「可逆」是本題**全新設計**，不是移植。

同時，這題處理的內容本身就是個資，規格上的任何含糊都可能讓使用者誤信「資料已經安全了」。本提案把六個關鍵設計判斷獨立成一節逐條定案，實作階段不再重新討論。

## 要改什麼

### 主要行為

- 貼上文字或拖曳 TXT / MD 檔案
- 規則偵測 Email、手機、市話、身分證字號；姓名為姓氏字典啟發式偵測
- 使用者手動指定姓名／敏感詞（沿用 v1 的字庫 textarea，但 v2 只需一個欄位，不需 v1 的「代換字庫」）
- 按鈕觸發「執行去識別化」：命中項替換為 Token（`[PERSON_001]`、`[EMAIL_001]` 等）
- 產生 mapping 表，畫面上以表格呈現（Token ↔ 原文 ↔ 類型 ↔ 出現次數）
- mapping 匯出 JSON / CSV
- 載入 mapping 檔，按鈕觸發「還原」，把 Token 換回原文
- 原文／結果並排
- **共通 UI 基線三項**（`shared/CONTRACT.md` 第 6 節明文規定，屬本系列產品慣例，**不視為違反共通開發規則第 3 條**）：複製結果到剪貼簿（`io-clipboard.js`）、下載結果檔案（`io-download.js`）、下載本工具離線版（`buildCleanHtmlCopy()`）

## 六個關鍵設計判斷（每條含決定與理由）

### 判斷 1：Token 碰撞與唯一性

**決定**

- Token 分配的鍵是 **`(類型, 正規化後的原始字串)`**，不是「實體」。同一鍵 → 同一 token；不同鍵 → 不同 token。
- 正規化規則（明定，實作不得自行擴充）：
  - Email：全轉小寫
  - 手機／市話：移除 `-`、`(`、`)`、半形與全形空白後比對；mapping 保存**第一次出現的原始寫法**（兩者共用同一組正規化規則，也共用同一個 `PHONE` token 類型）
  - 身分證：首字母轉大寫
  - 姓名、手動指定敏感詞：**完全字串相符，不做任何正規化**
- Token 前綴共 **6 種**：`ID`、`PHONE`、`EMAIL`、`PERSON`、`TERM`（手動指定）、`LITERAL`（判斷 2 用）。Token 格式 `[<PREFIX>_<NNN>]`。
- ⚠ **偵測器有 4 條 regex，token 類型只有 6 種，兩者不是一對一。** 手機與市話是**兩條格式不同的 regex，都要保留、都要比對**（`old/Day9/index.html:222-227` 的 `mobile` 與 `landline`），只是命中後**歸進同一個 `PHONE` token 類型**。實作時不得刪掉其中任何一條 regex；統一的只有 token 前綴，不是比對規則。（此為使用者裁示：原先規劃的手機／市話兩種 token 前綴，合併為單一 `PHONE`。）
- 編號各前綴獨立，依**首次出現位置**遞增，起始三位補零；超過 999 自然進位為四位（`[PERSON_1000]`），不歸零、不重用。
- **不同的人剛好同名 → 合併成同一個 token。** 工具不做實體消歧。
- **同一人的不同 Email → 兩個不同 token。** 工具不做實體合併。

**姓名匹配邊界與「同一人被截出不同長度」的規則（明定，實作不得自行變動）**

v1 的 `NAME_PATTERN` 是 `(姓)[一-鿿]{1,2}`，`{1,2}` 在 JS 是**貪婪**的，所以：

- 「王小明說」→ 匹配 `王小明`（姓 + 後兩字），不是四個字，也不是 `王小`。**採最長匹配，不做任何後綴詞截斷**（截斷需要一份停用詞表，那是 PRD 沒要求的新功能）。
- 副作用要誠實承認：「王小說話」會被匹配成 `王小說`，這是姓氏字典啟發式的固有誤判，靠判斷 4 原則 2 的「姓名＝姓氏字典啟發式，會誤判也會漏判」標示處理，不用演算法假裝解決。

當同一個人在不同上下文被截出不同長度時（原文 A 處是「王小明」、B 處只出現「王小」）：

- **token 分配鍵是實際匹配到的字面字串，不做前綴合併。** `王小` 與 `王小明` 是兩個鍵、兩個 token（`[PERSON_001]`、`[PERSON_002]`）。
- 理由：合併會直接摧毀雙射——`[PERSON_001]` 就無從決定該還原成 `王小` 還是 `王小明`，還原輸出必錯。「同一實體出現兩個 token」只是去識別化強度的損失，「一個 token 對應兩個字串」是正確性的崩壞，兩害相權必須選前者。
- 使用者的修正路徑是**既有功能，不新增 UI**：把完整姓名（`王小明`）填進「手動指定姓名／敏感詞」，`TERM` 優先序高於 `PERSON`，會覆蓋自動匹配（見判斷 6）。這句提示要放在偵測依據說明旁。

**理由**

可逆性的數學前提是 token 與原始字串之間的**雙射（bijection）**：一個 token 只能還原成一個字串，一個字串只能對應一個 token。任何「語意合併」（把兩個不同的 Email 合成一個 PERSON token）會讓映射變成多對一，還原時無從選擇，直接摧毀可逆性。而「同名合併」是雙射的必然後果——兩個「王小明」在字面上不可區分，工具沒有任何依據把它們分開；即使分開了，還原時也無法判斷哪個 `[PERSON_001]` 該還原成哪一個，反而製造錯誤還原。

同名合併的代價落在**去識別化強度**上：讀到 `[PERSON_001]` 的人會以為那是同一個人。這是規則式工具的固有限制，處理方式是**在 mapping 表格與說明中明說**「相同字面視為同一實體，本工具不做人物消歧」，而不是用演算法假裝解決。

正規化只在「同一個東西的不同寫法」這種**格式層**差異上使用（大小寫、分隔符號），因為那是可逆的機械變換；姓名與手動敏感詞不正規化，因為中文字串的任何正規化（全半形、繁簡）都會引入誤合併風險，而 mapping 保存原始寫法後還原仍能取回原樣。

### 判斷 2：還原正確性與 token 防碰撞

三個具體風險：(A) 原文本身就含 `[PERSON_001]` 這種字串；(B) mapping 的原文值本身含 token 字面；(C) 反覆全域取代時，前一輪還原出的內容被後一輪再次取代。

**決定**

1. **還原一律用 single-pass 掃描，禁止 `String.replace` 全域反覆取代。**
   實作方式：用一條 token regex（`/\[(ID|PHONE|EMAIL|PERSON|TERM|LITERAL)_\d{3,}\]/g`）對去識別化文字掃一次，逐一命中即查 mapping 並把替換結果**直接寫入輸出緩衝區**，輸出緩衝區的內容不再參與後續掃描。
2. **去識別化階段預掃描原文的 token 樣式字串。** 命中時：
   - 在偵測結果中列為獨立類型，替換成 `[LITERAL_NNN]`，mapping 記錄 `[LITERAL_001] → "[PERSON_001]"`（原字面）
   - 畫面上以明顯提示告知使用者「原文含 N 處 token 樣式字串，已一併處理」
3. **編號分配時避開原文中已出現的 token 字面。** 分配器先收集原文所有 token 樣式字面成一個集合，任何新分配的 token 若落在該集合內就跳過，取下一個編號。

**理由**

風險 B 與 C 的根源是同一個：把還原做成「對整份文字反覆取代」。single-pass 從演算法層直接消滅它們——mapping 值中的 token 字面永遠不會被二次替換，還原輸出與 mapping 的插入順序無關。這比「加逃逸字元」「用不可見字元包住 token」這類土法穩健，也不需要在 token 外觀上妥協（PRD 明寫 token 長 `[PERSON_001]` 這樣）。

風險 A 用 `LITERAL` 前綴收編。`LITERAL` 本身也在 token regex 的前綴集合內，所以原文若含 `[LITERAL_001]`，它同樣會被偵測、被分配成一個新的 `[LITERAL_NNN]`；配合決定 3 的「避開已出現字面」規則，新分配的編號不會撞上原文既有字面，加上 single-pass 還原，這條路徑是封閉且可證明正確的。

這三條合起來的驗證方式很具體：拿一份原文含 `[PERSON_001]` 與 `[LITERAL_001]` 的文字跑一輪去識別化再還原，比對還原結果與原文**逐字元相同**。這條會寫進 tasks 的驗收條件。

### 判斷 3：mapping 遺失時的介面表達

**決定**

- mapping **不寫入 localStorage / sessionStorage / IndexedDB**，頁面重整即消失。
- 去識別化完成後，結果區固定顯示一行狀態：**「mapping 尚未下載 — 關閉此頁面後將無法還原」**；使用者按下任一 mapping 下載按鈕後，改為「mapping 已下載（`<檔名>`）」。狀態列不可關閉。
- 「下載 mapping」是結果區的**主要視覺動作**（primary button），「複製結果」「下載結果」為次要。
- 還原分頁在未載入 mapping 時：「執行還原」按鈕 **disabled**，下方固定文案「本工具不保存 mapping，也沒有任何方式在缺少 mapping 時推回原文。」
- **禁止提供**任何「嘗試還原」「智慧還原」「猜測原文」「部分還原」入口，也不做「從 token 編號推測類型再填假資料」這類看似有用的功能。
- 還原時若文中出現 mapping 內沒有的 token：該 token **原樣保留不動**，並在結果區列出清單（見判斷 6 之外的邊界處理），文案為「不在 mapping 內，已原樣保留」，不是「還原失敗」也不是「已略過」。

**理由**

「不得宣稱可還原」不能只靠一句免責聲明，要靠**介面上不存在那個入口**。使用者對工具能力的認知主要來自可點擊的東西：只要畫面上有一顆按鈕叫「嘗試還原」，再多的說明文字都會被解讀成「大概還是有機會」。所以主要手段是 disabled 按鈕 + 沒有替代路徑。

未下載狀態列的設計理由是**時機**：使用者最可能弄丟 mapping 的時刻，是他剛拿到去識別化結果、興高采烈地複製走文字然後關掉分頁的那一刻。警語必須出現在結果區、在他複製結果的視線範圍內，而不是在頁面底部的說明段落。

Token 原樣保留（而非刪除、而非填 `[未知]`）的理由是**不破壞資訊**：使用者可能手上有第二份 mapping，或稍後才找到正確檔案。原樣保留讓他能再跑一次；任何替換都是不可逆的二次破壞。

### 判斷 4：不過度承諾的文案原則

不寫最終文案，定六條原則，實作與後續審稿都照這個檢查：

1. **主詞是工具做了什麼，不是資料變成什麼狀態。** 寫「本次找到 8 處並替換為 Token」，不寫「已移除所有個資」「文件已安全」。禁用詞表：安全、已保護、乾淨、完全、100%、全部、無虞。
2. **偵測方式與其限制同框顯示。** 每個類型旁標註依據：Email／電話／身分證標「格式規則」，姓名標「姓氏字典啟發式，會誤判也會漏判」。限制不能只寫在 README。
3. **責任歸屬寫在結果區，不藏進說明頁。** 結果區固定一行：「送出前請自行逐字檢查；規則式偵測必然有遺漏。」
4. **明列不做什麼。** 偵測設定區固定顯示「本工具不偵測：地址、生日、金融帳號、公司內部代號、職稱＋單位組合（除非你手動加入敏感詞）」。列出負面能力比宣稱正面能力更能防止誤信，也直接給了使用者「該手動加什麼」的線索。
5. **不使用安全語彙的視覺符號。** 不用綠勾、盾牌、鎖頭 icon，不用綠色表示「通過」。偵測 0 筆時顯示中性的「未命中任何規則」，並補「這不代表文中沒有個資」。
6. **動作按鈕照實命名。** 「執行去識別化」「執行還原」，不用「一鍵匿名」「保護我的文件」「安心送出」。

**理由**

過度承諾的傷害是**行為性**的：使用者相信工具已經處理乾淨，就不會自己再看一遍，於是漏網的個資直接寄出去。所以文案原則要對準「使用者會不會因此跳過人工檢查」這個行為，而不只是法律免責。原則 4（明列不做什麼）是這六條裡最有實效的一條——它把抽象的「不保證完整」變成使用者可以立刻採取行動的清單。

### 判斷 5：mapping 檔的加密

**決定：不做加密。改為做警告，且警告要跟著檔案走。**

- UI：mapping 表格上方固定一行警語（非 modal，不阻斷流程）：「mapping 檔含完整原始個資，等同還原金鑰。請與去識別化後的文字分開保存，勿一併寄出。」
- JSON 匯出：頂層加 `"_warning"` 欄位，值為同一句警語（放在最前面，開檔即見）
- CSV 匯出：第一行為註解列 `# 本檔含完整原始個資，等同還原金鑰，請勿外傳`，第二行才是欄位標題
- 預設檔名：`deid-mapping-DO-NOT-SHARE-YYYYMMDD-HHMM.json` / `.csv`（固定樣板，不含使用者輸入，避免路徑穿越）

**理由（三條）**

1. **PRD 沒要求。** PRD 05 MVP 列的是「產生 mapping」「mapping 匯出 JSON/CSV」，「不做」列的是雲端保存 mapping。共通開發規則第 3 條寫死「不自行增加未要求功能，不過度設計」，加密是新增功能，不是既有功能的正確性修補。
2. **半調子加密比不加密更危險。** 要做對，得用 WebCrypto + PBKDF2/Argon2 派生金鑰，附帶密碼強度提示、忘記密碼的不可救回說明、salt/iv 的正確處理與錯誤路徑——那是一整條獨立需求的規模，塞不進本題的 10 條任務。而 Base64、固定金鑰、XOR 這類「看起來加密了」的做法會製造安全錯覺，正好違反判斷 4 的整套原則，比不加密更糟。
3. **警告的成本是零，而且脈絡持久。** 加密保護的是「檔案落到別人手上」，警告保護的是「使用者自己不小心寄出去」——後者在實際使用中發生率高得多，且是本工具能實際影響的部分。把警語寫進**檔案內容與檔名**，是因為檔案會離開頁面脈絡（被拖進 email 附件、被丟進 Slack），UI 上的警語那時已經看不到了，只有跟著檔案走的文字還在。

**相關但不做**：不加「下載 mapping 前需勾選確認」的閘門。PRD 要求 mapping 可匯出，多一層勾選是設計膨脹，而且勾選框在第二次之後就變成肌肉記憶，實際防護值趨近於零。

### 判斷 6：手動指定與自動偵測的重疊處理

**決定**

- 區間去重**以 v1 為底**：`mergeAndDedupe()`（`old/Day9/index.html:308-322`）的排序策略（起始位置升冪、長度降冪）與 `detectAll()` 的來源優先序 `sensitiveMatches.concat(piiMatches)`（324-331 行）沿用；手動指定的敏感詞優先於自動偵測的個資，語意與 v2 需求對應。**但重疊時的動作要改**，見下一點。
- **重疊區間的處理由「捨棄」改為「合併」（v2 對 v1 的明確變更）**：v1 `mergeAndDedupe()` 用 `lastEnd` 游標把後來的重疊區間**整段丟掉**，所以手動敏感詞「小明」遇到自動偵測「王小明」時，會因為 PERSON 區間起始較早而勝出，「手動優先」在子字串情形下**其實失效**。v2 明定：

  - 兩個 match 的區間只要**有任何重疊**（含完全包含與部分重疊），就**合併成單一 match**：範圍取兩者**聯集**，type 取**優先序最高者**。
  - 例：手動 TERM `小明` 與自動 PERSON `王小明` 重疊 → 合併成一個 match，字面 `王小明`、type `TERM`、token `[TERM_001]`。文中若另有單獨出現、不與任何姓名匹配重疊的 `小明`，那是另一個鍵，拿另一個 token（`[TERM_002]`）。
  - 取聯集而非取較短者，是因為去識別化的失敗方向不對稱：多遮一個字只是可讀性變差，少遮一個字（例如只換掉 `小明`、留下 `王`）是個資外洩。
  - 合併後的字面仍是原文的**連續子字串**，雙射與 single-pass 還原都不受影響。

- **區間層合併之後，還要再加一步 v1 沒有的「type 歸併一致性檢查」（字串層）**：去重完成後，掃描所有 match，若同一個正規化字串在不同位置被判成不同 type（例如「李永昌」在 A 處被手動指定為 TERM、在 B 處只被自動姓名偵測命中成 PERSON，兩處沒有區間重疊，因此上一點的合併規則不會處理到），一律歸併到優先序最高的 type，優先序為 `TERM > ID > PHONE > EMAIL > PERSON`（`PHONE` 同時涵蓋手機與市話兩條 regex 的命中）。歸併後才進入 token 分配。
- 實作時要在程式碼註解記下：v1 `mergeAndDedupe()` 依賴 `Array.prototype.sort` 的**穩定性**（ES2019 起規範保證）才能讓 `start` 與長度都相同時 `sensitiveMatches` 勝出。這是隱含假設，測試要涵蓋這個案例。

**理由**

v1 的去重是**區間層級**的（決定文中每個位置歸誰），v2 的 token 分配是**字串層級**的（決定同一字串全域拿哪個 token）。兩者的粒度不同，v1 演算法沒有涵蓋後者。少了歸併這一步，同一字串在不同位置可能拿到 `[TERM_001]` 和 `[PERSON_003]` 兩個 token——雙射被打破，還原結果雖然仍正確（兩個 token 都指回同一字串），但去識別化強度變差（讀者能從 token 不一致推測出這是同一個詞），且 mapping 表格會出現重複列，看起來像 bug。

歸併優先序把 `TERM` 放最前，理由與 v1 當初的修正相同（見 `old/Day9/SECURITY_REVIEW.md` 第 5 節記錄的「李永昌」真實案例）：手動指定是使用者明確的意圖，自動偵測是猜測，明確意圖優先。

## v1 `SECURITY_REVIEW.md` 結論的適用性盤點

**仍然適用（v2 直接繼承，並列入本題資安檢視項）**

- 寫入 `innerHTML` 的內容一律先經 `escapeHtml()`（v1 §1、§2）——v2 的並排預覽、mapping 表格同樣渲染使用者輸入
- 零 `eval` / `new Function` / `fetch` / `XMLHttpRequest` / 外部資源載入（v1 §1）
- 「零對外連線是核心承諾」，需用 Network 面板實測全流程（v1 §3）——v2 加倍成立
- 下載檔名為固定字串、不受使用者輸入影響，無路徑穿越風險（v1 §4）
- 使用者輸入的敏感詞用 `String.indexOf` 精確比對、不編譯成 `RegExp`（v1 §1）——同時避開 ReDoS 與樣式注入
- 離線複本必須移除 `.nav-back` 與下載按鈕自己、清空所有輸入區（v1 §-1）

**因為「可逆」而失效或不足（v2 必須補的 delta）**

1. **最嚴重：v1 從未存在「產出物本身是機密」這個議題。** v1 遮蔽是破壞性的，原文資訊當場丟棄，最壞情況只是遮太多或漏遮。v2 產生的 mapping 是**完整原始個資的結構化集合**，是一個 v1 整份檢視都沒談到的高價值資產。所有結論都需重新以「這個工具會產生一個等同還原金鑰的檔案」為前提檢視。
2. **`buildCleanHtmlCopy()`（`old/Day9/index.html:515-549`）的清空範圍不夠。** v1 只清 `text-input`／`sensitive-input`／`substitute-input`／`file-name`／`detect-stats`／`detect-preview`／`toast`。v2 若照搬，下載出的「離線版 HTML」會**內嵌上一次的 mapping 與還原分頁內容**——而這個 HTML 正是設計來被分享與傳遞的檔案，等同把個資寫進一個會外流的產物。v2 必須擴充清空：mapping 表格 DOM、mapping 記憶體狀態、還原分頁的兩個 textarea 與已載入檔名、未下載狀態列。這一項要有獨立驗收條件（`grep` 下載出的檔案不含任何測試個資字串）。
3. **v1 §4 的「下載檔名固定」結論在 v2 不足。** v2 有三種下載（去識別化文字、mapping JSON、mapping CSV），路徑穿越風險仍為零，但新增了**使用者混淆**風險：把 mapping 誤當成去識別化結果寄出。需靠檔名自我區分（`DO-NOT-SHARE` 字樣）與檔案內建警語處理，這是 v1 沒有的要求。
4. **新增一個 v1 完全沒有的輸入來源：使用者載入的 mapping 檔（JSON / CSV）。** v1 的 XSS 檢視只涵蓋文字／機敏字庫／代換字庫三個 textarea。mapping 檔的內容既會被渲染成表格，也會被寫進還原輸出，且來自外部檔案（可能是別人給的）。`JSON.parse` 後必須逐欄位驗證型別（token 是否符合格式、原文是否為字串、有無原型污染鍵 `__proto__` / `constructor` / `prototype`），渲染前一律 `escapeHtml()`。CSV 解析同理，且不得用 `eval` 或動態 `RegExp`。
5. **v1 沒有本機持久化的議題，v2 有壓力。** v1 不保存狀態；v2 的「重整就失去 mapping」會產生加 localStorage 的誘惑。本題明確禁止任何持久化，並列入資安檢視項（`grep` 確認全檔無 `localStorage`／`sessionStorage`／`indexedDB`）。
6. **v1 §3 的承諾需擴充措辭。** 從「零對外連線」擴充為「零對外連線 + 零本機持久化 + mapping 不進入任何可分享產物（離線 HTML 複本、去識別化結果檔）」。
