# 提案：Day3 文字差異比對器 Round 2 —— 斷句顆粒度重構（Type D）

## 為什麼做

Round 1 修正後，真實文件（280 頁政府採購案）重跑統計為「新增 2279／刪除 258／修改 246／未變動 341」，經 Opus subagent 對整份比對輸出做系統性分類，判定 5 類雜訊來源中 **Type D（新舊版斷句顆粒度不一致）佔比最大**：目前 `splitIntoSentences` 的段落內合併規則完全依賴「該行有無句尾標點（。！？；）」決定是否併入下一行，且**沒有任何長度上限**——只要連續多行都不以句尾標點結尾，就會無限制合併成一個超長字串，再整體視為一句去比對。

從本 session 已貼上的真實文件可直接抓到具體反例（`Day3/index.html:2101` 現行邏輯下的實際行為）：

```
GPU 伺服器
1.CPU：Intel 6724P 3.6GHz(含)以上規格
2.RAM：512GB(含)以上規格
3.硬碟：6TB(含)以上規格
4.GPU：NVIDIA H200 x2（或同等品）含以上規格
5.隨機搭配微軟作業系統
2
```

這是一張硬體規格表，每一行都是表格儲存格內容，沒有一行以句尾標點結尾。現行邏輯會把這整段（含表頭、5 個規格項目、數量欄）合併成**單一一個「句子」**再進入 `diffArrays` 比對。新版把同一張表格重新排版（欄位順序調整、新增「規格如後：」等字樣）：

```
GPU 伺服器
規格如後：
1. 隨機搭配微軟作業系統
2. 處理器（CPU）：Intel 6724P 3.6GHz(含)以上規格(或同等品)
3. 記憶體 512GB(含)以上
4. 硬碟：6TB(含)以上
5. 圖形加速卡（GPU）：NVIDIA H200 x2（或同等品）含以上規格
```

兩邊都合併成一個超長字串後逐字比對，結果是**整張表被判為一整塊「修改」**，讀者完全看不出實際上只是欄位順序調整＋用詞微調，也無法定位到底哪一格真的變了。這類硬體規格表在該份採購文件中重複出現超過 20 次（GPU 伺服器、工作站、儲存設備等各節），是「修改」數偏高、且修改內容難以閱讀的主要原因。

## 要改什麼

只修改 `splitIntoSentences`（`Day3/index.html:2101`）的段落內合併判斷邏輯，新增一條「合併行數上限」規則：

- 目前：`buf` 只要沒遇到句尾標點就無限累加下一行，直到遇到標點或段落結束才切出。
- 改為：合併行數達到門檻（暫定連續 **4 行**）仍未遇到句尾標點時，強制把目前累積的 `buf` 當作一個獨立單位切出，不再繼續往下併——之後的行從新的 `buf` 重新開始累積。
- 理由：真實硬換行（PDF 頁寬固定寬度切斷的一句散文）通常只需要 2～3 行就會遇到句尾標點；連續 4 行以上都沒有標點，幾乎都是表格／清單被逐行抽取的結果，不是同一句話。此上限只是「防止無限合併」的保險絲，不改變原有「有標點就正常合併」的核心邏輯，也不新增段落判斷、不動 `normalizeForCompare`、`computeDiff`、字元級標示等既有邏輯。

具體行數門檻（4 行）會在任務中先用文件裡的真實表格反例與既有 8 組回歸測試共同驗證，若 4 行造成新的誤判（例如把本來該合併的正常散文硬換行切斷），視驗證結果調整為 3 或 5，門檻本身不是不可談判的常數。

## 影響範圍

- **只改**：`splitIntoSentences` 函式內的合併迴圈（新增行數計數與強制切出分支）。
- **不改**：`splitLineIntoSentences`、`normalizeForCompare`、`computeDiff`、`sentenceSimilarity`、字元級 diff、渲染、頁碼標記過濾、下載/複製功能。
- **需要重新驗證**：既有 8 組斷句回歸測試（含 Round 1 新增的頁碼標記、孤立標點測試）＋ 新增針對 Type D 反例的測試 ＋ 真實文件（280 頁）全量重跑，比對修改前後統計數字變化。
- **已知會保持不動的既有限制**：「清單多行保留」（`1.第一項\n2.第二項\n3.第三項` 這種每項都在門檻內、且部分項目本身可能以標點結尾的短清單）不在本輪修正範圍——本輪只解決「表格/長清單被合併成單一超長句子」的問題，不重構整個斷句顆粒度演算法。
