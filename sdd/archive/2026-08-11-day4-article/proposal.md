# 提案：撰寫 Day4「個資與機敏資料遮蔽工具」文章草稿

## 為什麼做

`Day4/README.md` 顯示程式碼已完成兩輪（初版＋規則式遮蔽/機敏字庫代換擴充），fresh agent 獨立驗收 9＋11 條驗收條件全數通過，但 `Day4/` 目錄下完全沒有 `article_draft.md`——文章連初稿都還沒開始寫。

Day4 的開發歷程有不少適合寫進文章的素材：跟使用者多輪釐清「個資 vs 機敏資料」該用什麼技術路徑處理（regex vs 使用者自訂詞庫）、機敏字庫與代換字庫的行號配對設計、實作階段用真實案例（「李永昌」同時符合姓氏字典與機敏字庫）抓到的重疊優先序 bug、以及統計數字計算範圍的疏漏。這些「規格反覆討論收斂」與「用真實測試案例抓出邏輯 bug」的過程，是文章「解題思路」與「Vibe 過程」段落的好素材。

## 要改什麼

依 `CHECKLIST.md`「文章產出」一節的固定結構，新增 `Day4/article_draft.md`，六段式撰寫：

1. **情境**：延續 Day2 PDF 轉 TXT/MD、Day3 差異比對的管線，承辦人員外傳文件前要先清掉個資與機敏內容，手動檢查容易漏看
2. **解題思路**：為什麼把「個資」與「機敏資料」拆成兩條不同技術路徑（regex+姓氏字典 vs 使用者自訂詞庫精確比對）、機敏字庫/代換字庫的行號一對一對應設計、個資規則式部分遮蔽（留頭尾/留末3碼/留@前1碼）取代單純遮蔽的取捨
3. **資源**：Playwright MCP、fresh agent 獨立驗收（兩輪）
4. **Vibe 過程**（本文重點）：跟使用者多輪釐清需求範圍的過程（從「機敏字眼可以選擇遮蔽或代換」到「機敏字庫/代換字庫兩個框、行號對應」的具體化）、實作階段用真實案例抓到的「機敏字庫被自動姓名偵測蓋掉」bug 與「統計數字誤算類別」bug，這兩個都是用真實測試資料跑出來數字對不上才發現，不是程式碼審查看得出來的
5. **產品**：功能清單、Playwright 截圖（含示範資料，能看出個資標示、機敏字庫直接代換的畫面）、GitHub Pages 連結（已上線，`curl -sI` 確認 200）
6. **心得與反思**：規格討論階段的反覆確認如何避免走錯方向、真實測試案例對抓出邏輯 bug 的重要性

## 影響範圍

- 只新增 `Day4/article_draft.md`，不改動既有程式碼
- 需要至少 1 張 Mermaid 圖（例如：個資 vs 機敏資料兩條技術路徑的架構圖，或機敏字庫/代換字庫行號配對邏輯）與 1 組 Playwright 實際操作截圖（含示範資料）
- GitHub Pages 連結已確認上線（`https://lushinshang.github.io/2026ironman/VibeCoding/Day4/index.html` 回應 200），文章可以直接放真實連結，不需要「待補」
- 若「Day4 單一 HTML 離線下載」提案（`sdd/day4-offline-download/`）也一併執行，文章第 5 節「產品」可以順便提到這個功能；但兩者是獨立提案，不互相依賴，文章不等離線下載功能做完才能寫
