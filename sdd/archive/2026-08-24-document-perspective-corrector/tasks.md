# Tasks：文件照片透視校正器（document-perspective-corrector）

> 前置條件：`sdd/img-infra/` 完成並驗收（`img-decode.js`／`img-canvas.js`／`img-perspective.js`／
> `img-file-size.js` 就緒）。本檔不包含「寫透視校正數學」之類的任務，直接引用契約第 6 節簽名，
> 見 `VibeCoding/shared/IMG_CONTRACT.md`。PDF 輸出任務（任務 9）的實作細節依 `proposal.md`
> 「待裁示」第 1 項的裁示結果套用，本檔先建立流程骨架與驗收框架。

- [x] 1. 建立 `Day17_document-perspective-corrector/src/index.html` 版面骨架與上傳流程：
  上傳區（接 `checkImageFileSize()` gate + `loadImageFile()`，讀檔前先過大小閘門，
  `reject` 時不讀檔）、圖片顯示畫布、四個角點的可拖曳覆蓋層（初始位置為圖片四個實際
  角落 `(0,0)`／`(w,0)`／`(w,h)`／`(0,h)`，正規化為 0–1 座標儲存為唯一真相）、
  旋轉／裁切／濾鏡控制區、Before/After 切換按鈕、JPG/PNG/PDF 輸出按鈕、三個共通按鈕
  （`CONTRACT.md` 第 6 節基線）；套用 `shared/base.css`。
  **驗收**：情境：上傳一張 90MB 的圖片，畫面顯示拒絕訊息且不進入 `loadImageFile()`
  （`>80MB` 一律拒絕）；情境：上傳一張正常尺寸的手機照片，畫面顯示圖片與四個角點，
  四個角點分別落在圖片畫布的四個角落（非圖片內縮位置，非畫面正中央）；情境：檢視
  儲存角點的資料結構，四個值都是 0–1 之間的正規化比例，不是像素座標。

- [x] 2. 實作 Tier 1 即時預覽：拖曳任一角點過程中（每個 `pointermove`），呼叫
  `solveHomography()` 算出目前四角對應的 3×3 homography，換算成 CSS `matrix3d(...)`
  套用在承載原圖的元素 `transform` 上，**不呼叫 `warpImageData()`**、不做任何 canvas
  像素重繪。
  **驗收**：情境：用滑鼠拖曳任一角點，畫面上的圖片即時（無明顯延遲、無跳幀感）跟著
  變形，`view-source` 或開發者工具確認拖曳過程中 `warpImageData` 沒有被呼叫（只有
  `transform` 樣式在變化）；情境：把四個角點拖回初始的圖片四角，畫面圖片變形消失、
  視覺上與原圖完全相同（因為此時 homography 為單位矩陣）。

- [x] 3. 實作 Tier 2 精確預覽：接 `shared/ui-debounce.js` 的 `debounce()`，拖曳停止
  150ms 後，對一份只需產生一次、長邊 800px 的縮小來源 canvas（`resizeCanvas({
  maxLongEdge: 800 })`）執行真正的 `warpImageData()`，取代 Tier 1 的 CSS 近似結果，
  顯示在 Before/After 的「After」畫面。
  **驗收**：情境：拖曳角點後放開滑鼠，等待約 150ms，畫面從 Tier 1 的 CSS 近似圖片
  切換成 `warpImageData()` 的精確校正結果（實測記錄兩者視覺差異，若肉眼可見明顯
  跳動或錯位在回報中誠實記錄）；情境：記錄縮小版 800px 長邊 `warpImageData()` 在瀏覽器
  的實際耗時（非契約已實測的 4032×3024 完整解析度數字），確認遠低於全解析度 192ms、
  不造成明顯卡頓；情境：連續快速拖曳角點多次（每次間隔 <150ms），中途不會觸發多餘的
  `warpImageData()` 呼叫，只有最後一次停止後才觸發一次。

- [x] 4. 實作手動旋轉（90° 倍數，角點選取前的步驟）：提供「向左轉 90°」「向右轉 90°」
  按鈕，套用後對來源 canvas 做旋轉重繪，四個角點重置回旋轉後新畫布的四個角落
  （正規化座標重新設為 `(0,0)`／`(1,0)`／`(1,1)`／`(0,1)`）。
  **驗收**：情境：對一張直式照片點擊「向右轉 90°」，畫面圖片變成橫式且旋轉方向正確
  （非鏡像、非顛倒）；情境：旋轉後檢查四個角點的正規化座標，回到四個角落的預設值
  （不是沿用旋轉前的座標，避免對錯位置）；情境：連續點擊「向右轉 90°」四次，圖片
  回到與原始方向一致的狀態（含尺寸）。

- [x] 5. 實作 Tier 3 完整輸出運算：使用者點擊「套用校正」時，把正規化角點座標換算成
  **原始解析度**來源 canvas（旋轉後、未縮小）的實際像素座標，呼叫一次完整的
  `solveHomography()` + `warpImageData()`，產生最終合成 canvas；目標矩形尺寸取
  來源四邊長的較大值以維持文件比例不失真。
  **驗收**：情境：對一張手機拍攝的斜拍公文照片，手動拖曳四角對齊文件四角後點擊
  「套用校正」，輸出結果是一張近似正面、矩形的文件影像（無明顯梯形透視變形），
  對應 PRD 驗收條件「四角調整後可把斜拍矩形校正成近似正面」；情境：記錄本次完整
  解析度運算在瀏覽器實測的耗時，與契約已實測的 Node 192ms 量級比較，若明顯超出
  （例如超過 1 秒）在回報中誠實記錄。

- [x] 6. 實作濾鏡：亮度、對比、灰階文件模式滑桿／開關，套用在 Tier 3 輸出的最終合成
  canvas 上（校正之後的獨立像素 pass），滑桿調整**只重繪濾鏡結果、不重新呼叫
  `warpImageData()`**。
  **驗收**：情境：套用校正後拖動亮度滑桿，畫面即時更新亮度且反應流暢（不因為連帶
  重跑透視校正而卡頓）；情境：開啟灰階文件模式，輸出圖片轉為灰階，色彩資訊被移除；
  情境：把亮度／對比／灰階全部歸零／關閉，輸出結果與剛完成 Tier 3 校正、尚未套用
  任何濾鏡時的結果一致（濾鏡是可逆的疊加層，不是不可逆修改原始校正結果）。

- [x] 7. 實作可選的二次裁切：在 Tier 3 校正完成的矩形結果上，提供一個可拖曳調整的
  裁切框，用來去除校正後邊緣殘留的裝訂孔、陰影等雜訊；裁切僅作用在已校正的輸出
  canvas 上，不影響角點資料或原始來源 canvas。
  **驗收**：情境：校正完成後拖曳裁切框縮小範圍並確認套用，最終輸出圖片只包含裁切框
  範圍內的內容，尺寸相應縮小；情境：不使用裁切功能（維持預設全範圍）直接輸出，
  結果與校正完成當下的矩形完全一致（裁切是可選步驟，不使用時不影響輸出）。

- [x] 8. 實作 Before/After 切換與「還原」：Before 顯示原始來源圖片（旋轉後、校正前），
  After 顯示目前最新的處理結果（依目前進度為 Tier 2 精確預覽或 Tier 3 完整輸出，
  取當下已計算出的最新結果）；「還原」按鈕把四角點、旋轉、濾鏡、裁切全部重置為初始
  狀態。
  **驗收**：情境：完成一次校正與濾鏡調整後點擊「Before」，畫面顯示未經任何處理的
  原始圖片；切回「After」，畫面顯示套用校正與濾鏡後的結果；情境：點擊「還原」後，
  四個角點回到圖片四角、旋轉角度歸零、濾鏡滑桿歸零，畫面回到與剛上傳時一致的狀態；
  情境：全程檢查使用者上傳的原始 `File` 物件／`ArrayBuffer` 內容未被寫入或修改
  （對應 PRD 驗收條件「原始圖片不被改動」）。

- [x] 9. 實作輸出：JPG／PNG 走 `canvasToBlob()` 對最終合成 canvas（校正＋裁切＋濾鏡
  後）輸出，經 `shared/io-download.js` 下載，檔名不與原始檔名相同；PDF 輸出先建立
  觸發按鈕與流程骨架，實作細節依 `proposal.md`「待裁示」第 1 項的裁示結果套用
  （方案 A：`window.print()` + `@media print`；方案 B：引入 jsPDF）。
  **驗收**：情境：點擊「下載 JPG」與「下載 PNG」，兩次下載的檔名皆與原始上傳檔名
  不同，檔案能被圖片檢視器正常開啟且內容為最終校正結果（對應 PRD 驗收條件「校正
  結果可獨立下載」）；情境：點擊「輸出 PDF」按鈕，依裁示方案觸發對應流程（方案 A
  應觸發 `window.print()` 並顯示只含校正結果的專用列印版面；方案 B 應直接下載一個
  `.pdf` 檔案），此驗收待裁示結果確定後補上明確斷言方式。

  四角點狀態、旋轉／濾鏡／裁切參數、Before/After 顯示狀態、`#__shared_toast` 元素，

  **驗收**：情境：完整操作一輪（上傳→旋轉→拖曳四角→套用校正→濾鏡→下載）後點擊
  「下載本工具離線版」，`file://` 開啟下載到的 `index.html`，重新走一次完整流程結果

  `document.querySelectorAll('.nav-back').length === 0`、載入時 `pageerror` 與
