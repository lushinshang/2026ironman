- [x] 1. 建立 `Day21_pdf-organizer/src/index.html` 版面骨架與多檔匯入流程：上傳區
  （接 `checkPdfBatchSize()` gate + `checkPdfFileSize()` 逐檔閘門，複用 `io-dropzone.js`
  的 `opts.multiple`）、來源檔案清單（檔名＋頁數）、頁面縮圖清單容器、輸出按鈕、
  三個共通按鈕（`CONTRACT.md` 第 6 節基線）；套用 `shared/base.css`。
  **驗收**：情境：一次選取 3 份 PDF（各自頁數不同），畫面顯示 3 個來源檔案項目，
  各自標示正確頁數；情境：上傳一份超過 100MB 的單檔，畫面顯示拒絕訊息且不進入
  `loadPdfFile()`；情境：匯入後 `state.sourceDocs` 與 `state.pages`（見 proposal.md
  資料結構）的內容與匯入的實際檔案頁數相符（例如 3 份各 5 頁的 PDF，`state.pages`
  長度為 15）。

- [x] 2. 實作縮圖渲染：對 `state.pages` 每一項呼叫 `renderPageToCanvas()` 產生縮圖，
  依匯入順序＋原始頁碼攤平顯示（尚未排序前的預設順序）。
  **驗收**：情境：匯入一份 10 頁 PDF，畫面顯示 10 個縮圖，依序對應第 1–10 頁，
  縮圖內容與該 PDF 用系統檢視器開啟同一頁的畫面一致；情境：匯入多份 PDF 後，縮圖區
  的來源標記（例如頁面角落顯示「A p.3」）能讓使用者分辨每個縮圖來自哪份原始檔案的
  第幾頁；情境：縮圖渲染耗時對於較大量頁數（例如 3 份各 20 頁＝60 頁）的批次記錄下來，
  若使用者明顯感受到卡頓（例如超過 3 秒才顯示完成）在回報中誠實記錄。

- [x] 3. 實作頁面拖曳排序（裁示 2 定案：真拖曳）：`state.pages` 每個縮圖項目可用
  pointer-based 拖曳（`pointerdown`/`pointermove`/`pointerup`，優先於 HTML5 native
  drag events 以取得較一致的觸控裝置支援）調整順序，拖曳中顯示插入線／佔位格視覺
  回饋，放開後 `splice` 取出再插入新位置。同一個拖曳操作也支援把頁面拖到不同的
  `groupId`（任務 5 的輸出群組）。
  **驗收**：情境：用滑鼠把清單中第 5 個頁面拖曳到第 1 個位置放開，該頁面的
  `sourceDocIndex`／`sourcePageIndex`／`rotation`／`groupId` 完整跟著移動到新位置，
  不因拖曳操作而遺失或錯位（Playwright `browser_drag` 驗證）；情境：跨文件拖曳排序
  （例如把來源 B 的某頁拖到來源 A 的頁面之間），結果正確反映在 `state.pages` 陣列
  順序；情境：拖曳過程中畫面顯示插入位置的視覺提示（插入線或佔位格），放開滑鼠前
  可以看到即將插入的位置；情境：在觸控裝置模擬（Playwright 的觸控事件或至少手動
  記錄一次真實觸控裝置測試結果，若沒有實體裝置可測，在回報中誠實記錄「僅驗證滑鼠
  拖曳，觸控相容性未實測」）。

- [x] 4. 實作旋轉與刪除（含復原）：點擊縮圖上的旋轉按鈕，該頁 `rotation` 以 90° 為
  單位遞增，縮圖即時反映新角度（CSS transform 預覽）；點擊刪除，標記
  `deleted: true`（不立即從陣列移除）；「復原上一步」還原最近一次的排序／旋轉／
  刪除操作。
  **驗收**：情境：對一個縮圖連續點擊 4 次旋轉，角度回到與原始一致的狀態；情境：
  刪除一個頁面後，畫面上該項目呈現已刪除樣式（半透明或打叉），但仍在畫面上可見
  （非直接消失），點擊「復原上一步」後恢復為未刪除狀態；情境：刪除後查看保留頁數
  統計（例如「保留頁數：40（2 頁已標記刪除）」），數字正確反映未刪除頁面數。

- [x] 5. 實作輸出群組管理（裁示 3 定案）：`state.groups` 預設含 1 個群組，所有頁面
  匯入時預設歸屬這個群組；提供「＋新增群組」按鈕與群組切換分頁籤，使用者可把頁面
  拖曳（沿用任務 3 的拖曳機制）到不同群組。刪除群組時，該群組內未刪除的頁面改歸屬
  預設群組（不允許頁面變成孤兒、沒有任何群組）。
  **驗收**：情境：初始匯入後只有 1 個預設群組，全部頁面 `groupId` 相同；情境：
  新增第 2 個群組後把 3 個頁面拖過去，這 3 頁的 `groupId` 更新為新群組、原群組不再
  包含這 3 頁；情境：刪除一個非預設群組，其內未刪除頁面的 `groupId` 改回預設群組，
  不會有頁面遺失或找不到所屬群組的情況。

- [x] 6. 實作輸出：對 `state.groups` 逐一處理，每個群組把 `deleted: false` 且
  `groupId` 相符的頁面依目前順序、各自 `rotation` 組成 `pageSelections`，呼叫
  `mergePdfDocs()` 產生一份 PDF。只有 1 個群組時透過 `io-download.js` 直接下載這
  一份 PDF；多個群組時用 `io-zip.js` 的 `createZipBlob()` 包成一個 ZIP 一次下載。
  檔名不與任何來源檔名相同。
  **驗收**：情境：匯入 2 份 PDF、調整順序、刪除 1 頁、旋轉 1 頁後（維持預設 1 個
  群組）點擊輸出，下載的新 PDF 頁數、順序、旋轉方向、內容皆與畫面當下的排列狀態
  一致（用系統 PDF 檢視器逐頁核對）；情境：建立 2 個群組並分別放入不同頁面後點擊
  輸出，下載得到一個 ZIP，內含 2 份獨立 PDF，各自內容對應正確群組的頁面；情境：
  輸出後重新檢查所有來源 PDF 的原始 `File` 物件／bytes 未被修改（對應 PRD 驗收
  條件「來源檔案保持不變」）。

- [x] 7. 顯示總頁數與即時統計：畫面持續顯示目前 `state.pages` 的總頁數（含已刪除，
  另外標注保留頁數），排序／刪除／旋轉操作後即時更新，不需要重新整理頁面。
  **驗收**：情境：初始匯入後總頁數與各來源 PDF 頁數加總相符；情境：刪除 3 頁後，
  總頁數不變但保留頁數減少 3；情境：復原刪除操作後，保留頁數恢復。

- [x] 8. 共通 UI 基線與整合驗收：複製結果（`shared/io-clipboard.js`，複製目前處理
  狀態摘要文字，例如「已匯入 3 份、共 42 頁、保留 40 頁」）；`buildCleanHtmlCopy()`
  清空已上傳 PDF、`state.pages`／`state.sourceDocs`／`state.groups`、排序與刪除狀態、
  `#__shared_toast` 元素，移除 `.nav-back` 與站內連結；建立 `src/bundle.json` 並跑
  `scripts/bundle.py` 產出 `index.html`／`bundle_manifest.json`。
  **驗收**：情境：完整操作一輪（匯入多檔→拖曳排序→刪除→旋轉→輸出）後點擊「下載本工具
  離線版」，`file://` 開啟下載到的 `index.html`，重新走一次完整流程結果一致；情境
  （比照既有題目慣例，測試 PDF 內容改用可辨識的哨兵文字，例如在測試 PDF 的頁面上
  印上 `ZZPDFORG` 字樣）：離線版載入後 `document.getElementById('__shared_toast')
  === null`、`document.querySelectorAll('.nav-back').length === 0`、載入時
  `pageerror` 與 console error 皆為空（Playwright 斷言，非原始碼 grep）；情境：
  `scripts/bundle.py` 執行後產出的 `index.html` 用 `file://` 與本機伺服器各測一次
  完整流程，上傳同一組測試 PDF 後輸出結果一致。

## 驗收條件（總結，抄自 PRD 18 並補充）

- 情境：可將不同 PDF 指定頁重新組成新 PDF（PRD 原文）。
- 情境：刪除與旋轉結果正確反映在輸出（PRD 原文）。
- 情境：來源檔案保持不變（PRD 原文）。
- 情境：拖曳排序操作不會造成頁面的來源歸屬（來自哪份檔案、第幾頁）錯位或遺失。
- 情境：輸出群組數量為 1 時效果等同單一輸出，>1 時每組各自輸出一份 PDF 並包成
  ZIP（裁示 3）。
